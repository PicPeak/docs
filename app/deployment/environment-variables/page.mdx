# Environment Variables

Complete reference for all PicPeak environment variables. Set these in the `.env` file at the project root.

<Callout type="warning">
Avoid `$` characters in passwords. Docker Compose interprets `$` as variable substitution. Either omit `$` entirely or escape it as `$$`.
</Callout>

Unless a section says otherwise, a variable works the same on the stable and the beta channel. Sections marked **beta channel only** describe features that are not in a stable release yet.

## Core

| Variable | Required | Default | Description |
|----------|----------|---------|-------------|
| `NODE_ENV` | No | `production` | Environment mode |
| `JWT_SECRET` | **Yes** (generated in Docker) | --- | Authentication secret. The Compose stack and the all-in-one image generate one on first start when it is unset and reuse it from their secrets volume. If you set it yourself it must be at least 32 characters, and the example values from older `.env` files are refused: the backend stops at startup with a message saying so. Generate one with `openssl rand -hex 32` |
| `TZ` | No | `UTC` | Timezone |
| `SHUTDOWN_TIMEOUT_MS` | No | `8000` | Backend shutdown deadline in milliseconds after `SIGTERM` or `SIGINT`; forces an exit when exceeded. Set in the backend container's environment and keep below Docker Compose's `stop_grace_period`. See [Stopping and restarting](/deployment/docker#stopping-and-restarting). |
| `TRUST_PROXY` | No | Compose: `1`; all-in-one image: `0`; unset: legacy private-range trust | How many reverse-proxy hops in front of the backend PicPeak trusts for `X-Forwarded-For` / `X-Forwarded-Proto`. See [`TRUST_PROXY`](#trust_proxy) below. |
| `EMAIL_QUEUE_ENCRYPTION_KEY` | No | `JWT_SECRET` | Encrypts invitation, password-reset and temporary-password variables, and gallery passwords and client PINs, while their emails wait in the queue. At least 32 characters (`openssl rand -hex 32`). Keep it unchanged while such mail is pending: a changed or lost key makes those queued messages fail instead of sending. If you rotate `JWT_SECRET`, set this to the old value first or let the queue drain |

### `TRUST_PROXY`

PicPeak keys rate limits, login lockouts and audit addresses on the client IP, and decides from `X-Forwarded-Proto` whether a request arrived over HTTPS. Both headers are only believed from proxies inside the `TRUST_PROXY` boundary. The value is anything Express' `trust proxy` setting accepts: a number of hops, `loopback`, `linklocal`, `uniquelocal`, a CIDR, a comma list, `true`, or `false`/`0`.

| Deployment | Default | Set it to |
|---|---|---|
| Compose stack, clients reach the frontend port directly | `1` (the bundled frontend nginx) | Leave it |
| Compose stack behind another reverse proxy (Traefik, Nginx Proxy Manager, Caddy, Cloudflare Tunnel) that forwards to the frontend port | `1` | `2` |
| All-in-one image, clients reach the container directly | `0` (no proxy inside the image) | Leave it |
| All-in-one image behind a reverse proxy | `0` | `1`, plus one for each further proxy in front |
| Native install, or an older compose file that does not set it | Legacy: trust loopback and every private-range address, with a warning at startup | The exact number of proxies in front of the backend, or `false` when there is none |

With too low a value every visitor appears under the proxy's address: one shared rate-limit budget, and five failed logins from anyone lock out logins for everyone for 15 minutes. With too high a value a client can choose its own address through `X-Forwarded-For`. A hop count is only safe when clients cannot take a shorter path to the app; that is why the Compose stack publishes the backend port on host loopback only. Never use `true` unless every path to the app crosses a proxy you control.

When `TRUST_PROXY` is `1` and a request shows another private-range proxy in front of the bundled nginx, the backend logs one warning per process suggesting `2`. See [Reverse Proxy → Client IP](/deployment/reverse-proxy#client-ip-rate-limiting-and-trust_proxy).

## Authentication cookies

Admin, gallery, and guest sessions are carried in HTTP cookies. These variables control how those cookies are set.

| Variable | Required | Default | Description |
|----------|----------|---------|-------------|
| `COOKIE_SECURE` | No | `auto` in production, `false` in development | `true`, `false`, or `auto` — see below |
| `COOKIE_SAMESITE` | No | `Lax` | `Lax`, `Strict`, or `None` |
| `COOKIE_DOMAIN` | No | --- | Set to `.example.com` only if serving cookies across subdomains |

### `COOKIE_SECURE` values

| Value | Behavior | When to use |
|---|---|---|
| _(unset)_ | `auto` when `NODE_ENV=production`, `false` otherwise | Default. Works for HTTPS and plain-HTTP installs |
| `auto` | Decide per request: `Secure` on HTTPS, not on HTTP | Mixed HTTPS + LAN HTTP access (see below) |
| `true` | Always set the `Secure` flag (HTTPS-only cookies) | Recommended once the site is only ever reached over HTTPS. Login over plain HTTP no longer works |
| `false` | Never set the `Secure` flag | Local/LAN-only deployments with no HTTPS |

The value is trimmed and case-insensitive; `1`/`yes`/`on` mean `true` and `0`/`no`/`off` mean `false`. Any other value is treated as `auto`, with one warning in the log at startup. The Compose files pass `COOKIE_SECURE=${COOKIE_SECURE:-auto}`. The installer writes `true` for installs behind a TLS proxy and `false` for plain-HTTP installs.

### Mixed HTTPS/HTTP deployments (`COOKIE_SECURE=auto`)

A common self-hosted setup:

- **Public**: HTTPS via a reverse proxy like Nginx Proxy Manager, Traefik, or Caddy (e.g. `https://photos.example.com`)
- **LAN**: Plain HTTP on a private address (e.g. `http://192.168.1.50:3000`, the frontend port) for admin access without going through the proxy

With `COOKIE_SECURE=true`, LAN login breaks because browsers refuse to send `Secure` cookies over HTTP. With `COOKIE_SECURE=false`, HTTPS login loses the security of the `Secure` flag. `auto`, the production default, decides the `Secure` flag per request — the backend reads `req.secure` from Express, which reflects the `X-Forwarded-Proto` header forwarded by your reverse proxy.

<Callout type="info">
**Requirements for `auto` mode:**
1. **Your reverse proxy must forward `X-Forwarded-Proto: https`** on HTTPS requests. Nginx Proxy Manager, Traefik, and Caddy do this by default. Custom Nginx configs need `proxy_set_header X-Forwarded-Proto $scheme;`.
2. **Your proxy must be inside the [`TRUST_PROXY`](#trust_proxy) boundary.** In the Compose stack that means `TRUST_PROXY=2` when a proxy forwards to the frontend port; on the all-in-one image `TRUST_PROXY=1`. A proxy outside the boundary is not believed, every request counts as plain HTTP, and cookies lose their `Secure` flag.
</Callout>

The backend port (`3001`) is published on host loopback only, so LAN access goes through the frontend port. To reach the backend port from another machine, set `PICPEAK_BACKEND_BIND_ADDRESS`.

## External-folder watching

Available in builds containing [PicPeak PR #1345](https://github.com/PicPeak/picpeak/pull/1345). These settings control automatic imports for reference-mode events. Each event must also opt in using **Watch folder for new files**; the global default does not enable watching for every event. See [External Media](/features/external-media#watch-a-folder-for-new-files) for setup, permissions and deletion behaviour.

| Variable | Required | Default | Description |
|----------|----------|---------|-------------|
| `EXTERNAL_MEDIA_WATCH` | No | `true` | Global service switch. Set `false` to stop automatic external imports for all events; saved per-event watch settings remain unchanged. |
| `EXTERNAL_MEDIA_WATCH_POLLING` | No | `false` | Use repeated filesystem metadata checks instead of notifications. Useful for NFS/SMB shares that do not report writes from other machines. |
| `EXTERNAL_MEDIA_WATCH_POLL_INTERVAL_MS` | No | `5000` | File polling interval when polling is enabled (5 seconds). |
| `EXTERNAL_MEDIA_WATCH_SWEEP_INTERVAL_MS` | No | `900000` | Full scan of watched folders every 15 minutes as a fallback. `0` disables this scan. |
| `EXTERNAL_MEDIA_WATCH_DEBOUNCE_MS` | No | `10000` | Quiet period after the last detected new file before starting an import (10 seconds). |
| `EXTERNAL_MEDIA_WATCH_STABILITY_MS` | No | `5000` | Settling interval for new files (5 seconds). Automatic passes defer recently modified or changing files and retry later. |
| `EXTERNAL_MEDIA_WATCH_RECONCILE_INTERVAL_MS` | No | `60000` | Advanced: how often the backend re-reads event watch settings (1 minute). Add this explicitly to Compose's backend `environment` block if overriding it. |

All interval values are in milliseconds. The updated bundled Compose files forward the first six options from `.env`; they do not forward `EXTERNAL_MEDIA_WATCH_RECONCILE_INTERVAL_MS`. Custom Compose definitions must pass the desired variables through `environment` or `env_file`. On AIO, set them on the PicPeak container. Recreate the container after changes; for a native process, restart the backend with the new environment.

The watcher uses the local `EXTERNAL_MEDIA_ROOT` with both local and S3 storage backends. These settings do not configure the managed-storage file watcher or the S3 prefix walker.

## Docker user mapping

`PUID` and `PGID` are no longer read. The backend container starts as root, hands its bind mounts to UID 1001 and drops privileges; to run as another UID, pin `user:` in a compose override. See [Docker → Permissions](/deployment/docker#permissions).

## Upload limits

Limits on what the server admits, set as JSON in the backend environment and applied after a restart. Empty means the defaults; omitted keys keep their default. Sizes are integer bytes, counts positive integers. Unknown keys and zero, negative or fractional values are refused. The defaults are the same on the stable and the beta channel. The full reference is [`docs/PUBLIC_UPLOAD_LIMITS.md`](https://github.com/PicPeak/picpeak/blob/main/docs/PUBLIC_UPLOAD_LIMITS.md) in the code repository.

| Variable | Required | Default | Description |
|----------|----------|---------|-------------|
| `PUBLIC_UPLOAD_LIMITS_JSON` | No | see below | Limits on **public** uploads only: gallery guests and PicTransfer file requests. Photographer, admin, API and import uploads never count |
| `ADMIN_UPLOAD_LIMITS_JSON` | No | see below | Authenticated uploads (admin UI, API token, resumable uploads, PicTransfer files). These are never rate-limited or charged; only what is in flight at once is bounded |

Public defaults: one request carries at most 95 MiB (never less than one file of the configured maximum size). Lifetime allowances, which deleting a file does not give back:

| Scope | Lifetime | Concurrent requests | Per hour |
|---|---|---|---|
| Gallery | 50 GiB / 20,000 files | 16 | 20 GiB |
| Guest | 50 GiB / 20,000 files | 16 | 20 GiB |
| File request | 50 GiB / 20,000 files | 4 | 20 GiB |
| Account | 500 GiB / 200,000 files | 32 | 100 GiB |
| Deployment | unlimited (free-disk headroom) | 64 | 200 GiB |

Admin defaults: at most the smaller of 50 GiB and 25% of free space staged at once, 50,000 staged files, 16 concurrent requests per admin account, 64 per deployment, 10 minutes per request or chunk. Both profiles keep 512 MiB and 1,024 inodes free (inodes only where the filesystem counts them); `headroomPercent` additionally keeps a share of the volume free and is off by default.

```dotenv
PUBLIC_UPLOAD_LIMITS_JSON={"requestBytes":209715200,"gallery":{"bytes":107374182400}}
ADMIN_UPLOAD_LIMITS_JSON={"stagedBytes":214748364800,"accountRequests":32}
```

Larger request bodies also need matching limits in your reverse proxy.

## Contract signing evidence

Beta channel only. See **[Contracts](/features/crm/contracts)**.

| Variable | Required | Default | Description |
|----------|----------|---------|-------------|
| `PICPEAK_EVIDENCE_KEY` | No | key file `storage/business-docs/keys/evidence.key`, created with the first signature | Key that encrypts each signer's name, email address, IP address, user agent and decline reason. 64 hex digits or 43 characters of base64 are used as the key itself; any other value is treated as a passphrase. Use a raw 32-byte key in production (`openssl rand -hex 32`): a passphrase is derived with a fixed salt, so the evidence is only as strong as the passphrase, and every start logs a warning while one is configured. A value that is one or two characters off a key is refused at startup. When unset, PicPeak generates the key file; once it exists, every start logs a warning asking you to back it up |
| `PICPEAK_EVIDENCE_KEYS_OLD` | No | (unset) | Earlier evidence keys, comma-separated, in the same forms as `PICPEAK_EVIDENCE_KEY`. Evidence written under one of them stays readable while `scripts/rotate-evidence-key.js` moves it to the current key; new evidence is always written under the current key. A malformed entry is refused at startup. Needed only while rotating |

### Losing or changing the evidence key

Each stored value names the key it was written under. PicPeak reads it with the current key, any key in `PICPEAK_EVIDENCE_KEYS_OLD`, and any file named `evidence.key.<keyId>` next to the key file in `storage/business-docs/keys/`. New evidence is always written under the current key.

- **Losing the key** that evidence was written under, with no copy anywhere, makes those signer names, email addresses and IP addresses unreadable. The signatures, the signed PDFs and the signing event log stay valid.
- **Recovery** means making the lost key readable again: put its value in `PICPEAK_EVIDENCE_KEYS_OLD`, or restore its file as `evidence.key` (if it is the current key) or `evidence.key.<keyId>` (if it is an old one).
- **System Health** shows the key in use, how many stored values are still under an older key that can be read, and how many are under a key PicPeak no longer has.

#### Rotating the key

1. Set `PICPEAK_EVIDENCE_KEY` to the new key. Keep the old one readable: put it in `PICPEAK_EVIDENCE_KEYS_OLD`, or — if the old key was the generated key file — leave the file where it is.
2. Restart the backend.
3. Run the rotation script:

   ```bash
   docker compose exec backend node scripts/rotate-evidence-key.js --dry-run   # counts per key, changes nothing
   docker compose exec backend node scripts/rotate-evidence-key.js
   ```

   On its first run it keeps a replaced generated key file as `evidence.key.<keyId>`, then re-encrypts every value that is under another key, in batches. It is safe to stop and run again at any time: a run re-encrypts only values still under another key, so a second run after a complete one changes nothing. A signature recorded while it runs is never overwritten; it is skipped and picked up by the next run. It prints how many values it moved and how many are still under another key.
4. Keep the old key until the script reports **0 values still under another key**, then remove it from `PICPEAK_EVIDENCE_KEYS_OLD` (or delete the `evidence.key.<keyId>` file).

Rotation changes only the encrypted values. The content hash, the PDFs, the signing certificate and the signing log's hashes stay exactly as they were.

Back up `PICPEAK_EVIDENCE_KEY` (and any old keys still needed) with your other secrets, or the key files with the database. They sit under `business-docs`, which is part of the backup export.
