# Video Support

PicPeak supports uploading and displaying videos alongside photos in event galleries.

## Supported formats

| Format | Extension |
|--------|-----------|
| MP4 | `.mp4` |
| WebM | `.webm` |
| MOV | `.mov` |
| AVI | `.avi` |

## Enabling video

Video is **off by default**: the [Allowed File Types](/guides/admin-settings/general#allowed-file-types) list ships as `jpg,jpeg,png,webp`. Add the video extensions you want to accept, for example:

```
jpg,jpeg,png,webp,mp4,mov,webm
```

That single list governs the admin upload screen, the admin chunked-upload API and guest uploads. Until the extensions are added, the upload screen hides video files in its picker and the chunked API answers `400 File type not allowed` — the MIME type a request declares does not override the list.

## Upload limits

- Per-file cap: **Max Video Size (MB)** in General settings (default 500 MB), separate from the photo cap. Raise it, and the reverse-proxy body limit below, for long recordings.
- Large files go through the admin chunked-upload API (10 MB chunks, resumable per chunk) — see [Photos API](/api/photos#chunked-upload-large-files).

## Browser playback

The gallery plays the file you uploaded. Browsers decode H.264 in an MP4 container; an HEVC (H.265) recording from a recent phone plays in Safari and nowhere else, a QuickTime `.mov` is unreliable outside Safari, and an MP4 whose index sits at the end of the file has to download whole before the first frame. For those files the guest sees "This video format cannot be played in this browser" and a download link.

**Browser-playable copies of videos** in [General settings](/guides/admin-settings/general) fixes this at ingest. It is off by default. Switched on, a background worker checks every video and, for anything a browser will not play, writes an H.264/AAC MP4 (streamable, at most 1920 px on the long edge) next to the original. The gallery then streams that copy; the download stays the original file. A video that already plays as it is gets no copy.

What to expect:

- Switching the setting on queues every video already in your galleries. The worker takes them one at a time; a transcode runs at roughly real time on a small server, so a large back catalogue takes a while. Nothing changes for guests until each copy is ready, and the setting can be switched off again at any point.
- The copies live in PicPeak's storage (also on S3), including for videos imported from an external folder — the originals on the share are never touched. Plan for the extra space: a 1080p copy is typically 10–20 MB per minute.
- When a copy cannot be made, the video's tile on the admin Media tab carries a **No web copy** note with the reason, and the original keeps playing as before. Switching the setting off and on again retries failed copies.
- Needs FFmpeg with the `libx264` encoder, which the PicPeak images include.

Tunables for the worker are listed under [Environment Variables → Video copies](/deployment/environment-variables#video-copies). Builds containing [PicPeak PR #1761](https://github.com/PicPeak/picpeak/pull/1761).

## Thumbnail generation

Video thumbnails are automatically extracted from the first few seconds of each video using FFmpeg. The Docker images ship FFmpeg (`ffmpeg` and `ffprobe`); on a native installation, install it from your distribution and make sure it is on the backend's `PATH`.

When FFmpeg cannot read a file, the video gets a neutral placeholder tile with a play icon instead of a poster frame. On the admin Media tab that tile carries a **No poster frame** note with FFmpeg's reason, and a **Retry** that takes the poster frame again — useful after installing or updating FFmpeg. Builds containing [PicPeak PR #1760](https://github.com/PicPeak/picpeak/pull/1760).

### Missing thumbnails repair themselves

In builds containing [PicPeak PR #1417](https://github.com/PicPeak/picpeak/pull/1417), a video whose thumbnail is missing or unreadable --- typically one uploaded on a much older version --- is repaired the first time someone opens its gallery: PicPeak takes the poster frame again and stores it, so it happens once per video. Older builds showed a broken tile for these videos. No action is needed after updating.

On **S3 storage** the repair has to download the video from the bucket first. To keep a guest's gallery visit from triggering multi-gigabyte downloads, videos larger than `VIDEO_THUMBNAIL_MAX_SOURCE_BYTES` (default 512 MB) get the placeholder tile instead of a poster frame. Raise the value in your [environment](/deployment/environment-variables#storage-backend) if your videos are routinely larger and you prefer real poster frames. The limit does not apply to local storage, to external folders, or to new uploads.

## Resource requirements

<Callout type="warning">
Video processing is resource-intensive. Plan your server resources accordingly.
</Callout>

| Resource | Recommendation |
|----------|---------------|
| RAM | 4 GB+ recommended |
| Storage | Plan for 10-100x more than photo-only galleries |
| CPU | Additional cores help with thumbnail extraction |
| Bandwidth | Video streaming requires higher throughput |

## Reverse proxy configuration

If using Nginx as a reverse proxy, increase the body size limit and timeouts:

```nginx
client_max_body_size 10G;
proxy_read_timeout 3600;
proxy_send_timeout 3600;
```

Without these settings, large video uploads will be rejected by the proxy before reaching PicPeak.
